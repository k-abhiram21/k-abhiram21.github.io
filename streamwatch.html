02 THE MAIN PROBLEM

What’s happening
inside the application?

Our brief was to monitor an unstructured database. We needed a way to see what the MongoDB application was doing, follow request activity, and explore the data it held.

I worked on instrumentation, the monitoring integration, and the frontend that brings those views together.

04 ONE INTEGRATION DECISION

Getting query activity
into Grafana.

We were asked to show query activity alongside the monitoring data. Numeric metrics alone didn’t carry the context we wanted in Grafana.

I worked on custom instrumentation that attached query context to metric labels, making it available to the dashboard.

Debugging it meant checking the whole path, from what the application exposed to what the panel actually displayed. This was one part of the wider MongoDB monitoring workspace.

A closer look at the integration ↓

How the two paths connect.

React talks to the FastAPI application, which connects to MongoDB. For AI-assisted querying, Gemini translates the question into a MongoDB query. Monitoring follows a separate path: the backend exposes instrumentation at /metrics, Prometheus collects it, and Grafana produces the panels.

What we instrumented.

The backend tracks client query traffic with user, client, and query-type labels, alongside a packet-size histogram. A custom gauge also carries the AI query’s question, generated MongoDB query, result, and status in its labels. That is how query context reaches the dashboard through the metrics pipeline.

Putting the panels in React.

MetricFrame.jsx builds a Grafana panel URL from the dashboard, panel ID, and active theme. Vitals.jsx brings together panels for client traffic, packet-size distribution, system metrics, and query activity. I worked across that connection: exposing the application’s activity and making the resulting panels available in the workspace.
