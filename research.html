02 INTERNSHIP / LLMLENS / PHASE 1

CHARACTERIZING DETECTION LIMITS

How far does
uncertainty get us?

A model can repeat the same wrong answer.

That makes response consistency an interesting signal, but an incomplete one. The study examines how well uncertainty signals distinguish correct answers from hallucinations across model and task settings.

MY CONTRIBUTION

First author; research question, methodology, experiment software, analysis, and manuscript writing, with coauthors and supervision.

MANUSCRIPT · WITH EDITOR AT KAIS

Where Internal Signals Fail: Characterizing the Performance Ceiling of Uncertainty-Based Hallucination Detection

Submitted to Knowledge and Information Systems.

How I approached the investigation ↓

Check the setup.

A detector score is only as useful as the comparison behind it. I checked the experiment code, reference labels, and scoring behavior before interpreting differences between methods. This helped separate an issue in the evaluation from a pattern worth studying.

Examine difficult cases.

Incorrect answers with reassuring signals were especially useful to inspect. The analysis asked how those cases behaved across settings, and which observations held beyond a single comparison.

Write what the evidence supports.

The manuscript connects each finding to the conditions under which it was measured. The analysis and writing focused on making those conditions clear enough for a reader to assess the conclusion.

03 INTERNSHIP / MY ROUTING WORK / PHASE 2

ROUTING IMPLEMENTATION & EVALUATION

When should we use
a different answer?

The same specialist can help on one request and hurt on another.

The question is when switching improves the answer for the current task, and what evidence supports that decision.

MY CONTRIBUTION / ROUTING

Routing implementation and debugging, including verification and evaluation tooling. The wider framework is shared research work.

FRAME

What changes?

Compare the answer returned before and after a routing decision.

INVESTIGATE

What does it cost?

Account for the generation and checking needed to make that choice.

REFINE

What if it fails?

Include the fallback path when checking the system’s behavior.

From the research question to working code ↓

Agree on the decision.

The router, verifier, and serving path need a common understanding of a routing outcome. I work on the interfaces between them so that the response selected by the code matches the decision recorded for evaluation.

Follow the selected answer.

A decision is more than a score in a log. I trace which response reaches the caller and how verification affects that path. This makes mismatches between a component’s output and the system’s final behavior easier to locate.

Keep fallback behavior explicit.

When a path cannot be used, the remaining choice needs to be well defined. I include those cases in implementation checks so that handling a failure remains part of the decision layer.

Debugging the decision layer ↓

Reproduce the unexpected choice.

I start with the request and follow its path through the code. The aim is to establish which components ran, what each returned, and where the final choice diverged from the intended behavior.

Separate code from assumptions.

A bug calls for a correction; an assumption calls for an experiment. Establishing which one caused the result keeps the next change focused. It also helps explain why a plausible-looking output is not enough to judge the implementation.

Check the correction.

Once the cause is understood, I use focused checks to see whether the change addresses it and whether nearby paths still behave as expected. Verifier integration and failure handling are part of that review.

Building and checking the evaluation tools ↓

Compare the same task.

Routing needs to be assessed against the base response under comparable conditions. I work on evaluation code that keeps the inputs, selected outputs, and scoring aligned, so a result can be traced back to the choice that produced it.

Inspect unusual measurements.

If a result changes unexpectedly, the evaluation machinery is one of the places I inspect. Data handling and scoring errors can change a comparison before the routing logic has improved at all.

Include the cost of the choice.

Generating another response or adding a verifier takes work. The evaluation needs to account for that effort alongside answer quality, so the comparison reflects what the system actually had to do.
